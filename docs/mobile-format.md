# 移动版备份与资源格式

适配对象是曾验证过的 jubeat plus / jukebeat iMazing `.adbk` 备份，解密实现依据 Jubeat.app 3.9.11 的 BFCodec 行为整理。不能假定所有后续版本都使用相同格式。

第一次阅读建议先看 [带手算示例的导读](walkthrough.md)。本页进一步拆解密码算法和图片转换，源码分别是 [jbf.c](../mobile/tools/jbf.c)、[extract.py](../mobile/extract.py) 和 [cgbi.py](../mobile/tools/cgbi.py)。

## 处理链

```text
.adbk ZIP
  └─ 应用目录/Documents/<ID>.jbt ZIP
       ├─ info / infov2 → 解密 → Apple binary plist
       ├─ seq_bas / seq_adv / seq_ext → 解密 → 事件 → .mc
       ├─ artwork 等 → 解密 → CgBI → 标准 PNG
       └─ bgm / index → 解密 → AAC/M4A
```

只读取已知歌曲条目。`Documents/scImg/*.img` 可选导出，应用设置、账号、成绩数据库和未知条目不会导出。

## BFCodec 变种

- 16 轮 Blowfish，P/S 初始表使用标准常量。
- F 函数为 `(S0[a] + S1[b]) XOR (S2[c] + S3[d])`，加法按 32 位回绕。
- 密钥为格式固定口令 `Konami Bemani Mobile iPad` 的 MD5 摘要：`f9a142c70b07d9a8093b56b8c2eeb698`。
- CBC IV：`e36631da2c85a064`。
- 条目布局：`密文 || 明文长度 BE32 || 密文长度 BE32`。密文长度为 8 的倍数，解密后按明文长度截断。

这些常量属于文件格式，不是用户账号、设备凭证或 API 密钥。标准 Blowfish 库无法直接代替本变种。源码中旧的 IV 注释与实际常量曾不一致，本仓库已统一为上述值。

### 第一步：准备密钥，而不是对资源做 MD5

先把固定口令的 ASCII 字节做 MD5，得到 **16 个二进制字节**。代码中的 32 个十六进制字符只是这 16 字节的可读表示；不能把那 32 个字符直接当密钥。MD5 在这里仅用于得到格式所需的密钥，不承担文件解密或完整性验证。

### 第二步：把密钥展开成查找表

`jbf.c` 顶部的大段数字是 Blowfish 的公开初始 P/S 常量。P 表有 18 个 32 位数，四张 S 表各有 256 个 32 位数。它们不是歌曲数据，也不是 1,042 个独立密钥。`keysetup` 会复制这些表，再混入固定密钥：

1. 每四个密钥字节按大端组成一个 32 位数，逐项异或到 P 表；密钥用完后从头循环。
2. 从 `L=0, R=0` 开始，使用当前表进行一次 16 轮加密，把结果写回 P 表的前两项。
3. 继续加密上一步的结果，依次替换剩余 P 表和四张 S 表，每次替换两项。
4. 完成后得到供全部数据块复用的展开表。

一共替换 `18 + 4×256 = 1042` 个数，即 521 次分组加密。**展开时调用的也是变种 F 函数**，所以“初始常量相同”不等于“展开后的轮密钥与标准库相同”。只修改普通库的数据解密循环、保留原密钥展开，也会得到错误结果。

### 第三步：一块八字节怎样还原

把一个 64 位块按大端拆成左右两个 32 位数 `L,R`。F 函数把一个数拆成高到低四个字节 `a,b,c,d`，每个字节作为对应 S 表的索引。

| 算法 | F 函数，所有加法均按 32 位回绕 |
|---|---|
| 标准 Blowfish | `((S0[a] + S1[b]) XOR S2[c]) + S3[d]` |
| 本仓库 BFCodec 变种 | `(S0[a] + S1[b]) XOR (S2[c] + S3[d])` |

标准定义可核对 [Blowfish 原论文的算法部分](https://www.schneier.com/academic/archives/1994/09/description_of_a_new.html)。BFCodec 这一行以本仓库整理的实现为依据；标准论文不描述游戏的变种。

括号的位置改变了“先相加还是先异或”，两个式子一般不相等。C 的 `uint32_t` 自动按 32 位回绕；移植到 Python 等任意精度整数语言时，加法后需要 `& 0xffffffff`。

`decblk` 可按以下等价伪代码理解，P 下标从 0 开始，循环使用同时赋值：

```text
for k = 17, 16, ..., 2:
    x = L XOR P[k]
    L, R = R XOR F(x), x

输出左半块 = R XOR P[0]
输出右半块 = L XOR P[1]
```

这就是逆序使用轮密钥的 16 轮 Feistel 还原。读 C 时的 `hi`、`lo` 分别是 F 两侧的和；几次异或合起来等价于上面的 `R XOR F(x)`。它的输出还不是文件明文，因为外面还有 CBC。

### 第四步：CBC 把块连接起来

令 `C[i]` 为第 i 块密文，`D` 为上述单块解密：

```text
M[0] = D(C[0]) XOR IV
M[i] = D(C[i]) XOR C[i-1]    (i > 0)
```

`M[i]` 表示明文块。当前密文须先留作下一块的链值；不能把上一块**明文**拿来异或。每个 ZIP 资源成员都重新使用 IV，不能把上一首歌或上一个条目的最后一块继续接上去。

尾部与缓冲区的约束是：

```text
clen == 输入长度 - 8
clen % 8 == 0
0 <= plen <= clen
clen - plen < 8
输出缓冲区容量 >= clen
```

最后一块即使只保留一个字节，循环仍会先写满八字节，因此缓冲区不能仅按 `plen` 分配。全部块还原完后才截到 `plen`。这个封装没有实现 MAC 认证；长度合法只能证明结构可处理，不能证明密文没有被改动。

人工样例可直接复核：零填充的 `hello` 对应密文 `d9437e92fe3cbbad`，随后是尾部 `00000005 00000008`。它由公开的 Python 参考加密器生成，并用 C 解密器还原；不来自游戏文件。

### 并发与验证

轮密钥必须先串行展开，再由工作线程只读复用。曾有旧实现每次解密都改写全局轮密钥，导致并发音源错位；当前 Python 封装用锁确保只初始化一次。

该保证适用于当前固定密钥封装；如果绕过 Python 直接调用 C，并在解密过程中调用 `jbf_setkey` 换密钥，仍会改写全局表。C API 本身没有为这种用法加锁。

核对解密规则时，应同时看多种资源是否恢复成可解析结构：例如 `info` 的 plist、`seq` 的记录边界、PNG 的块结构和可解码音频。某几个字节“看起来像文件头”证据不够。原始逆向过程与当前可公开复现的验证范围分开列于 [验证说明](validation.md)。

## 谱面

`seq_*` 解密后是小端记录流：

| 偏移 | 内容 |
|---|---|
| `0x00` | 4 字节标识，如 IJBQ / IJSQ / IJBS |
| `0x04` | 记录条数 `u32` |
| `0x08` | note 记录计数 `u32`，不要直接当作含尾判的物量 |
| `0x0c` | 总 tick `u32` |
| `0x12` | marker 位掩码 `u16` |
| `0x60` | 记录数组，每条为两个 `u32` |

`type = r0 & 255`，`tick = r0 >> 8`，`value = r1`。

| type | 含义 |
|---|---|
| 1 | 单点，value 为 0..15 面板位置 |
| 2 / 3 / 4 | END / MEASURE / HAKU |
| 5 | TEMPO，value 约为 `floor(60000000 / BPM)` |
| 6 | 长押，与 IFS 的 LONG 使用相同位段 |

长押：`index = value & 15`，`direction = (value >> 4) & 3`，`length = (value >> 6) & 3`，`duration = value >> 8`。实现使用的 `(dx, dy)` 为 `0:(0,-1)`、`1:(0,1)`、`2:(-1,0)`、`3:(1,0)`，终点坐标为起点加方向乘长度。这里明确坐标增量，避免把箭头指向与终点方向混淆。

tick 为 300 Hz。TEMPO 变化形成分段时间轴，使用有理数积分，再按 1/48 拍量化。极短长押可能量化成同拍头尾，仍保留长押；统计物量采用 `tap + 2 × hold`。

二进制记录、长押 `76880` 的位运算、120→60 BPM 的完整计算，以及量化误差见 [导读第 4～7 节](walkthrough.md#4-两种谱面怎样归一成相同事件)。`magic`、计数与 marker 掩码会读入，但当前转换器并未完整验证这些字段的版本含义，也不会靠它们还原游戏的 marker 行为。

## CgBI PNG

CgBI 图片使用裸 deflate、预乘 BGRA。转换时解 PNG 行过滤、恢复 RGBA、解除 alpha 预乘并重新压缩为标准 PNG。实现限制输入体积与像素总数，校验分块和解压长度；普通 PNG 可直接透传。

仅删掉 `CgBI` 标记或改文件后缀不够，实际有三层差异要处理：

1. **压缩流**：合并 IDAT 块，用 `zlib.decompressobj(-15)` 解裸 deflate；标准 PNG 的 IDAT 则使用 zlib 封装。
2. **行过滤**：每行开头的字节指定预测方式，后面的字节可能是与左侧或上一行的差值，必须先恢复成真实通道数值。
3. **像素含义**：交换 B/R 通道，并把乘过 alpha 的颜色恢复为非预乘值，再用普通 zlib 流写出 PNG。

标准 PNG 的压缩、过滤与 alpha 表达可核对 [W3C PNG 规范](https://www.w3.org/TR/png-3/)。这里的 CgBI 差异来自本实现及样本验证，不属于该规范。

`_unfilter` 对每个通道字节进行以下恢复，加法取模 256；左邻指前一个像素的同通道字节，RGBA 的间距是四字节：

| filter | 加回的预测值 |
|---|---|
| 0 None | 0 |
| 1 Sub | 左邻 |
| 2 Up | 上邻 |
| 3 Average | `floor((左邻 + 上邻)/2)` |
| 4 Paeth | 从左、上、左上中选最接近 `左+上-左上` 的值，平局按规范次序处理 |

没有的邻居按 0 处理。还原过滤后，对每个预乘颜色通道 `c`，在 `0 < a < 255` 时计算：

```text
straight = min(255, (c * 255 + a // 2) // a)
```

例如原始 BGRA 是 `[25,50,100,128]`，交换顺序并解除预乘后得到 RGBA `[199,100,50,128]`。红色是 199 而不一定是 200，因为预乘及整数量化已丢失信息。`a=0` 时输出 RGB 全零，无法恢复完全透明像素原来的颜色；`a=255` 时只需交换通道。

转换器目前只处理 8 位 RGBA、非交错的 CgBI，输出行使用 filter 0，重算 PNG 块 CRC。输入侧检查块范围、IEND 和解压后长度，但**不逐块校验输入 CRC**；因此不能将它当作完整 PNG 验证器。图片转换异常在歌曲处理阶段会跳过该图片，音频和谱面仍可导出。

## 输出与限制

- 每首歌曲分别保存三难度 `.mc`、图片、音频和元数据。
- `.mcz` 可保留 AAC 或转 Vorbis；谱面中的音频引用与实际成员名一致。
- 未提供音频、封面时不写悬空引用。
- 输出目录必须为空；包与 ID 隔离避免把移动版和街机同名谱面混在一起。
- 结构越界、缺少必需谱面和超预算输入会失败；部分图片失败会跳过。未知版本不一定被自动识别，成功运行不能替代内容核对。
